# Snap 75/25 layout, woven-felt tray, and cross-platform hole-view input

Three features land together on `feature/snap-layout`: the main UI is restructured into a Marvel-Snap-style band where the 3D hole fills the top 75% and a felt tray holds the hand/Shoot button in the bottom 25% (FEAT-001); a procedural woven-felt + stitched-brass-rail canvas_item shader is assigned to that tray and the turf/rough grain is pushed harder via mesh `.tres` overrides and a finer noise octave (FEAT-002); and `hole_viewer.gd` gets a full cross-platform input pass — tap-vs-drag aim, touch/trackpad gestures, keyboard camera, and on-screen zoom/rotate/reset buttons — with the retired putting path preserved behind a null guard (FEAT-003). The whole change is UI/UX + input only; no gameplay, turn-loop, hole-gen, scoring, or card logic is touched beyond re-parenting the hand UI, and `hex_grid.gd` is untouched.

Watch for: the hand UI re-parent hinges entirely on `unique_name_in_owner` surviving the move — confirmed preserved on all four of `%HandStrip`/`%ClubRow`/`%ModifierRow`/`%ShootButton` (confirmed). On-device touch and trackpad behavior cannot be proven by the headless gates by design; the gesture handlers are verified wired and non-throwing in code, not exercised live (confirmed static / untestable runtime).

**Verdict**: APPROVED

## High-level view

The layout restructure is driven entirely from `main_ui.tscn` plus a five-line `@onready` switch in `main_ui.gd`. The HoleViewer instance overrides all eight layout props to defeat the base scene's `anchors_preset=9`/`offset_right=800` inheritance and occupy the 0..0.75 band; a new `%Tray` PanelContainer takes the 0.75..1.0 band. The four hand-UI nodes move into the tray and the five HUD readouts move into a mouse-ignoring `HoleHUD` overlay on the hole band, all keeping their unique names so no gameplay wiring breaks.

The felt is a self-contained `canvas_item` shader assigned as a `ShaderMaterial` on the tray, with the FEAT-001 `StyleBoxFlat` left underneath as a fallback so the tray still reads dark if the shader fails to compile. The turf/rough intensity bump is pinned in the four mesh `.tres` files (the values that actually render); the shader-file default bumps are consistency-only.

The input overhaul routes touch and trackpad gesture events ahead of mouse handling in `_input`, and introduces a shared tap-vs-drag discriminator so a left-click or single finger only aims on a quick stationary release — a drag promotes to a pan and never fires an aim. Two-finger pinch/twist, trackpad magnify/pan gestures, and keyboard camera actions are added; `reset_view()` now restores pitch as well as yaw; and touch putting forwards a synthesized mouse event behind a `putting_system == null` guard that keeps the retired path dormant but intact.

### Layout re-parent rests on unique_name_in_owner surviving the move

The entire "zero script edits for the hand UI" claim depends on `unique_name_in_owner` being position-independent: a `%` lookup resolves from the MainUI owner as long as the node stays in MainUI's owned subtree and the flag stays set. The diff confirms all four hand nodes (`HandStrip`, `ClubRow`, `ModifierRow`, `ShootButton`) moved from floating bottom-center anchors into `Tray/TrayMargin/TrayContent/...` with `unique_name_in_owner = true` intact and their names unchanged (confirmed). The five HUD nodes re-parented under `HoleViewer/HoleHUD` likewise carry the flag, and `main_ui.gd` switches exactly those five (`wind_widget`, `lie_view`, `hole_info_label`, `generate_button`, `generate_unique_button`) from `$Name` to `%Name` while leaving `hole_viewer`/`shot_ui`/`combined_deck_widget` as `$` direct children (confirmed). `DeckWidget` stays present and hidden, so the typed `@onready var combined_deck_widget: DeckWidget` does not null/type-error on load (confirmed).

The HoleViewer instance overrides all eight layout props (`anchor_*`, `offset_*`, `grow_*`) rather than relying on inheritance, which is necessary because the base `hole_viewer.tscn` root carries `anchors_preset=9` and `offset_right=800` that would otherwise leak through (confirmed).

### Viewport draw-order fix for the HUD overlay

`_setup_viewport()` adds a `move_child(viewport_container, 0)` so the code-created 3D viewport sits at the bottom of HoleViewer's draw order. Without it the viewport would be the last child and paint over the `HoleHUD` overlay (wind/lie readouts, Generate buttons, on-screen HoleControls) authored in the scene. This is a real consequence of hanging the HUD off HoleViewer and the fix is correct (confirmed).

### Aspect-aware framing

`_center_on_hole()` now fits the hole along both its length (Z, via `Z_FIT_FACTOR=0.55`) and width (X, via `X_FIT_FACTOR=2.0` divided by viewport aspect), with a 16/9 fallback and a guard that skips framing when `viewport == null or viewport.size.y <= 1` and retries on the next resize. `viewport_container.resized` drives `_on_viewport_resized()`, which re-frames only when the camera is idle — not tracking the ball and not `is_panning`/`is_rotating`/`is_pitching` — so a window resize never yanks a tracked or mid-gesture camera (confirmed).

### Felt tray shader with StyleBox fallback

`felt_tray.gdshader` is a `canvas_item` shader reusing turf's `hash2`/`value_noise`, building a basket-weave over/under mask from two orthogonal sine ridges with per-cell alternation, plus value-noise fuzz and a dashed brass rail. It uses the built-in `TAU` directly — the FEAT-002 findings record an earlier `const float TAU` redefinition that failed compile and was removed, and the committed shader has no such declaration (confirmed). It is assigned as a baked-default `ShaderMaterial` on `%Tray.material` while the `StyleBoxFlat_tray` panel remains as `theme_override_styles/panel`, so the tray still reads dark if the shader ever fails to compile (confirmed). `main_ui.gd` feeds `tray_aspect` from the live tray size on `resized`, guarded against a non-`ShaderMaterial` material and `size.y <= 0` (confirmed).

The four mesh `.tres` files carry exactly the intended pinned values (fairway grain 0.07 / stripe 0.06; green grain 0.06; rough tuft 0.11 / scale 20.0; deeprough tuft 0.13 / scale 20.0) with geometry and `base_color` untouched; `turf.gdshader` mixes a finer `value_noise(wxz*18.0)` octave into the grain while keeping the matte ROUGHNESS/METALLIC/SPECULAR block (confirmed).

### Tap-vs-drag discriminator keeps pan from stealing aim

The shared discriminator is the load-bearing piece for aim correctness across desktop and touch. A left-mouse press or first finger-down arms `pending_tap` without aiming; motion past `TAP_MOVE_THRESHOLD` (10px) clears the pending tap and promotes to a single-pointer pan; release aims via `_handle_tile_click` only if the press stayed under threshold and under `TAP_TIME_THRESHOLD` (350ms). The `is_interacting` check in the button branch now includes `pending_tap`, so the viewer owns the release even when it started as a possible tap (confirmed). The synthesized `InputEventMouseMotion` fed from the touch-drag path only sets `.position`, and `_handle_mouse_motion`'s pan branch reads `event.position` against `pan_start_mouse` (not `.relative`), so the synthetic event drives panning correctly (confirmed).

### Gesture and keyboard paths are wired but only statically verified

`_input` routes `InputEventScreenTouch`/`ScreenDrag`/`MagnifyGesture`/`PanGesture` to dedicated handlers before mouse handling. Two-finger pinch/twist are computed as independent axes with `prev_dist`/`prev_ang` seeded when the second finger lands; `_handle_magnify_gesture` re-seeds `prev_dist` so the drag-pinch path won't double-apply in the same frame. Keyboard camera (`cam_rotate_left/right`, WASD/arrows, `cam_zoom_in/out`) runs in `_process_keyboard_camera`, gated off focused `LineEdit`/`TextEdit` and `_is_mouse_inside()` so it doesn't fight text entry or fire over the tray. All referenced symbols (`set_zoom`, `is_pitching`, `camera_yaw`, `putting_system`, `pan_speed`, etc.) exist in the file (confirmed).

These branches cannot fire on a headless desktop run, so the recorded evidence proves they compile and don't throw — not that pinch/twist/pan feel right on a phone or trackpad. That is inherent to the gate and matches the FEAT-003 acceptance criterion ("compile and do not throw on a desktop headless run where they never fire"); genuine on-device validation is out of reach here (confirmed static, untestable runtime).

### project.godot stays input-only; retired putting preserved

`project.godot` changes are confined to a new `[input_devices]` `pointing/emulate_mouse_from_touch=false` and new `[input]` actions (`down`→S, `cam_pan`→Space, `cam_rotate_left`→Q, `cam_rotate_right`→E, `cam_zoom_in`→`=`/`+`, `cam_zoom_out`→`-`). No gameplay settings changed and the `custom_font="uid://csixfh5trj68q"` line (source of the 2 accepted baseline font errors) is untouched (confirmed). `cam_pan` is defined but not yet bound to a Space-hold-pan mode — the FEAT-003 findings note this as a deliberate leave-for-later, not a gap, since pan is already reachable via drag/PanGesture/WASD. Touch putting forwards a synthesized press+release to `putting_system.handle_input` behind a `putting_system == null` early return, and `_handle_putting_mouse_button` and the putting branches are left intact, so the retired system stays a safe no-op while preserving the mouse contract if un-retired (confirmed).
